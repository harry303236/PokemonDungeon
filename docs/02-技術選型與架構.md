# 02 技術選型與架構

## 1. 技術棧（已決定）
| 項目 | 選擇 | 理由 |
|---|---|---|
| 引擎 | **Phaser 3.80+** | 成熟的 2D web 引擎，內建 tilemap、粒子、相機、輸入；文件與範例多，AI agent 熟悉 |
| 語言 | **TypeScript 5（strict）** | 資料驅動系統需要強型別；方便重構 |
| 建置 | **Vite 5** | 快速 HMR、靜態輸出，可部署到任何 CDN |
| 測試 | **Vitest** | 和 Vite 同生態 |
| Schema | **zod** | runtime 驗證 JSON＋推導 TS 型別 |
| 資料管線 | `tsx scripts/fetch-pokeapi.ts` | 開發時抓 PokeAPI 並快取，輸出靜態 JSON |
| Lint | ESLint + Prettier | — |
| 存檔 | localStorage（M5 之後可換成 IndexedDB） | 單機、零後端 |
| 套件管理 | npm | — |

不選 Godot／Unity：要 web 一鍵遊玩、AI agent 能直接讀寫純文字程式碼、co-op 用 WebRTC。

## 3. 模組邊界
- `core` → 只依賴 `data/registry`；對外輸出 `Sim`（`step(dt, inputs)`）與 EventBus。
- `render` 訂閱 EventBus 與讀取 ECS 狀態做繪製，**不改遊戲狀態**；只透過 `InputCommand` 把操作送進 `core`。
- `ui` 讀取 store（`core/state-store.ts` 的 snapshot），寫入時只送 command（例：`EquipItemCommand`）。
- 這樣切分的目的：core 可以 headless 測試，co-op 時 host 跑 sim，client 只渲染。

## 4. ECS 決策：用「輕量自製 ECS」
- 理由：大量投射物／地帶／怪物（目標同屏 300 個實體 @60fps）；詞綴系統要給任何實體掛 tag／listener，組合需求高。不引入 bitecs 等第三方，避免 AI agent 卡在 API 細節。
- 實作：`World` 存 `Map<ComponentName, Map<EntityId, Component>>`；`EntityId = number`；`query(...names)` 回傳 id 陣列（每 tick 做快取）。
- 元件（初版）：`Transform{x,y,rot}`、`Velocity`、`Collider{radius,layer}`、`Health{hp,maxHp,shield}`、`Stats`、`Faction{team:'player'|'enemy'}`、`PokemonRef{speciesId,level}`、`MoveLoadout`、`Cooldowns`、`Energy`、`StatusSet`、`TagSet`、`Projectile`、`Zone`、`AIState`、`Lifetime`、`Loot`、`Owner{entity}`、`HitHistory`。
- 系統執行順序（`sim.ts`）：`input → ai → moveCast → movement → collision → hitResolve → damage → statusTick → zoneTick → weatherTick → death → loot → lifetime → cleanup`。

## 5. EventBus
- 同步、型別安全：`bus.emit<K extends keyof GameEvents>(k, payload)`。
- `GameEvents`（完整清單見 `04` §6.2）：`move:cast`、`projectile:spawn`、`hit:pre`、`hit:post`、`damage:dealt`、`status:applied`、`status:expired`、`tag:applied`、`tag:consumed`、`entity:killed`、`weather:changed`、`terrain:changed`、`player:levelup`、`player:evolve`、`loot:dropped`、`floor:cleared`。
- 每個 payload 都帶 `chain: ChainContext`（遞迴保護，見 `04` §6.4）。
- render/ui 用另一個「表現層」bus（`ui-bus`），由 core 事件轉發，延遲一 tick 也沒關係。

## 6. 遊戲狀態機（Phaser Scenes）
```
Boot(載入 generated JSON + assets) → Title(新遊戲/繼續/設定)
 → StarterSelect(只有新遊戲時) → Hub(城鎮：配招/技能樹/背包/選地城)
 → Dungeon(+UIScene 疊加) ⇄ Pause
 → FloorTransition → Dungeon(下一層) … → Victory/GameOver → Hub
```
- 進入 Hub、離開地城、進化、每 60 秒，都要自動存檔。地城中途的進度**不存**（MVP）。

## 7. 存檔格式
- key：`pokedungeon.save.v{N}`；另有 `pokedungeon.settings`。
- JSON 結構見 `03` §SaveData。必有 `version: number`；`migrations.ts` 依序升版。
- 寫入：JSON.stringify →（M5 之後可加 LZ-string 壓縮）；寫入前先備份到 `pokedungeon.save.bak`。
- 讀取失敗：從 .bak 還原，再失敗就提示玩家並另存一份 `corrupt-{timestamp}`。

## 8. 效能預算
- 60 fps @ 1080p、中階筆電；同屏實體 ≤ 300、粒子 ≤ 2000。
- 碰撞：均勻網格空間雜湊（cell 64 px）。
- 物件池：投射物、傷害數字、粒子發射器。

## 9. Co-op（M5 之後，先預留介面）
參考概念（自行重新實作）：host 權威；reliable ordered WebRTC DataChannel；15 Hz 狀態快照＋事件；signaling 先用 WebSocket／Firebase 等任一種簡單服務；天氣這類全域事件由 host 決定後廣播。MVP 要求：所有遊戲輸入都經過 `InputCommand`、sim 有確定性（seed RNG），之後才能接網路。
